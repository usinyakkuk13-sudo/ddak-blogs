# 블로그 글쓰기 판단기준 (마스터)

이 문서는 우리 블로그 글의 "좋은 글이란 무엇인가"를 정의한다. 사이트별 톤은 각 `sites/<슬러그>/_ANGLE.md`에, 여기엔 **모든 사이트 공통 기준**을 둔다. 글을 쓰기 전에 이 문서 → 해당 사이트 `_ANGLE.md` → `config.py` 순으로 읽는다.

목표: 개수가 아니라 **한 편의 확실한 원본 글**. 애드센스는 도메인 단위 심사이므로 얄팍한 글 여러 개보다 읽을 가치 있는 글 하나가 승인·노출에 유리하다.

## 1. 주제 선정 — "갭 사냥"

좋은 주제의 조건은 셋 다 충족:

1. **검색 수요는 있는데 제대로 정리된 글이 드문 것**(갭). 웹검색으로 "이 주제로 검색했을 때 상위 글들이 부실한가?"를 확인한다.
2. **바로 써먹는 실용 정보**가 들어갈 수 있는 것 — 구체적 금액·조건·신청 순서·전화번호·기한처럼 독자가 오늘 행동으로 옮길 수 있는 내용.
3. **기존 글과 안 겹칠 것**. 담당 사이트 `content/`의 기존 제목·slug를 먼저 훑어 중복·유사 주제를 피한다.

피할 주제: 이미 잘 정리된 레드오션, 시의성 없는 뻔한 요약, 사이트 정체성과 무관한 것.

## 2. 글 구조 (기본 틀)

- **도입(후킹)**: 독자의 실제 막막함을 한 문장으로 짚는다. "등급은 나왔는데 뭘 신청하지?" 같은 진짜 질문으로 시작. 서론은 짧게.
- **본문**: `## 소제목`으로 논리 단위 구분. 각 소제목 아래는 2~5문장 문단 + 필요 시 목록/표.
  - **표(`| |`)**: 금액·등급·조건 비교처럼 수치가 여럿이면 반드시 표로. 스캔이 쉬워진다.
  - **단계 목록**: 신청·절차는 번호 목록으로.
  - **`<div class="tip">...</div>`**: 놓치기 쉬운 팁·예외·주의 1개를 박스로 강조.
  - **예시**: "4등급이면 월 약 141만 원, 본인부담 약 21만 원" 처럼 **구체 숫자로 예를 든다.**
- **마무리**: 반드시 `## 정리` 소제목으로 핵심을 3~5줄 압축. "우리 부모님은 뭘 고르면 좋을까요?" 같이 독자 상황에 대입해주는 문단이면 더 좋다.

분량: 한국어 **1,500자 이상**. 얄팍한 요약·중복 금지.

## 3. 톤·문체

- **큰 개념을 쉬운 말로.** 전문용어는 쓰되 바로 옆에 풀어준다("재가급여 = 집에서 받는 돌봄서비스").
- 존댓말, 독자를 존중하는 다정한 어조. 과장·낚시·불안 조장 금지.
- 사이트별 정체성은 `_ANGLE.md`를 따른다(예: 든든한 노후 = 큰 글씨·쉬운 말·"이거 하나로 해결"의 든든함).
- 문장은 짧게. 한 문단이 5줄을 넘기면 쪼갠다.

## 4. YMYL 가드레일 (건강·복지·금융·부동산)

돈·건강·제도를 다루는 글은 신뢰가 생명이다. 반드시:

- **수치·통계·고유명사·기한은 웹검색으로 실제 출처 확인.** 확인 못 하면 지어내지 말고 일반화하거나 "관계 기관에서 확인" 안내로 대체.
- 글 안에 **"정확한 내용은 관계 기관(복지로·건강보험공단·국민연금공단·정부24·주민센터 등)에서 확인하세요"** 취지 문장 포함(generator가 하단 고지문을 자동 삽입하지만, 본문에서도 자연스럽게 짚어준다).
- **부동산·투자**: 예측·매수/매도 권유가 아니라 "양측 논리·지표 해설 + 투자조언 아님" 관점.
- 금지: 특정 정당·후보 홍보/선동, 실존 인물 허위 인용·비방, 저작권 전재(방송분·대본 등), 세대·집단 비하, 성적/미성년 유해, 개인식별정보(실명·전화·주소·계좌) 노출.

## 5. front matter (맨 위, 정확히)

```
---
title: "구체적이고 검색될 제목 (연도·핵심키워드 포함)"
description: "검색결과용 한 줄 설명(120자 내외, 무엇을 얻는지 명확히)"
date: (드립 공개용 규칙 ↓)
category: (해당 사이트 config.py의 한글 카테고리명 중 하나)
slug: 영문-소문자-하이픈 (기존과 중복 금지)
tags: 태그1, 태그2, 태그3
---
```

- **date = 드립 규칙**: 담당 사이트 `content/`의 모든 .md 중 **가장 늦은 date보다 하루 뒤** 날짜를 넣는다(기존 글 없으면 오늘). 빌드는 date가 오늘 이하인 글만 공개하므로 새 글은 대기열 맨 뒤에 붙어 하루 1편씩 순차 공개된다.
- **title**: 검색될 실제 질의를 반영. 연도가 의미 있으면 넣는다("...총정리 (2026년)").
- 파일 경로: `sites/<담당슬러그>/content/<slug>.md` (UTF-8, 추가만 — 삭제 금지).

## 6. 저장 전 품질 체크리스트 (셀프 리뷰)

글을 파일로 쓰기 전에 스스로 통과 여부를 확인한다. 하나라도 아니오면 고친다.

- [ ] 이 주제, 상위 검색결과보다 우리 글이 더 쓸모 있나? (갭 충족)
- [ ] 독자가 오늘 행동으로 옮길 구체 정보(금액·순서·기한·연락처)가 들어있나?
- [ ] 1,500자 이상이고, 표/목록/tip 박스로 스캔이 쉬운가?
- [ ] 모든 수치·고유명사를 웹검색으로 확인했나? 못 한 건 일반화했나?
- [ ] `## 정리`로 끝맺고, YMYL이면 확인 안내 문장이 있나?
- [ ] front matter의 date가 드립 규칙(가장 늦은 글 +1일)에 맞나? slug·category 유효한가?
- [ ] 기존 글과 주제·제목이 겹치지 않나?
- [ ] 금지 항목(정당 홍보·허위 인용·저작권·비하·개인정보)에 안 걸리나?

## 7. 빌드

프로젝트 루트에서 `python3 build_all.py`. 오류 나면 고쳐서 다시 빌드. 편집 도구가 큰 파일을 잘라먹는 버그가 있으니 `generator.py` 등 코드 수정은 bash로 하고 문법 확인 후 빌드한다.
